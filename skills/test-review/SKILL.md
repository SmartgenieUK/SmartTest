# Test Review

## Purpose

Judge test quality and evidential adequacy against intended behaviour, not merely test existence or execution status.

## Use when

- Reviewing test changes in a pull request or release candidate.
- Assessing tests generated by the same agent that wrote an implementation.
- Investigating whether a green suite protects an acceptance criterion.
- Deciding what evidence is still missing before release.

## Inspect

Inspect:

1. Requirements, acceptance criteria, change intent, and risk.
2. Relevant implementation diff and affected contracts.
3. Authoritative existing tests plus changed or added tests.
4. Test helpers, fixtures, mocks, snapshots, data, and environment configuration.
5. Execution results and provenance when available.
6. Change-impact analysis or plausible downstream consumers.

Do not infer adequacy from filenames or test counts.

## Procedure

1. Map each material acceptance criterion and risk to existing evidence.
2. Check happy paths, boundaries, invalid and negative paths, failures, recovery, permissions, integrations, and regression as applicable.
3. Confirm each test asserts an observable consequence strong enough to fail for a relevant defect.
4. Look for assertions that only restate setup, snapshots that approve broad output, swallowed failures, always-true conditions, and missing awaits or equivalent false-positive paths.
5. Check whether mocks preserve the material contract and whether real integration evidence is required.
6. Check brittleness against implementation detail and whether tests protect behaviour during safe refactoring.
7. Look for tests derived from current implementation rather than independent intent, especially when the same context produced both.
8. Assess test data, determinism, reproducibility, and retained evidence.
9. Check regression protection across the plausible blast radius.
10. Where consequence warrants it, inspect mutation, fault-injection, negative execution, or review evidence showing tests can detect defects.
11. Classify findings by whether they block an explainable assurance claim.

## Required output

Use exactly this structure:

```text
VERDICT: PASS | FAIL | ESCALATE

Blocking findings
Non-blocking findings
Missing evidence
Strong existing evidence
Recommended additions
```

For every finding, identify the affected requirement or risk, supporting evidence, and consequence. A PASS must explain why the evidence is sufficient and list any residual risk or N/A decision. Use ESCALATE when adequacy cannot be decided without missing authority, requirement clarity, environment, or material evidence.

## Stop or escalate

Escalate when:

- intended behaviour or acceptance criteria are materially ambiguous;
- relevant tests, results, data, environment, or dependency evidence are unavailable;
- an accepted risk or waiver requires an accountable human decision;
- a high-consequence integration cannot be evaluated from the available repository.

Fail rather than escalate when evidence is available and demonstrably inadequate.

## Anti-patterns

- Pass because tests exist or CI is green.
- Count scenarios without tracing them to intent.
- Approve assertions that cannot detect the target defect.
- Demand integration tests where lower-level evidence is sufficient, or accept mocks where the real boundary is the risk.
- Treat another AI review as automatically independent.
- Recommend duplicating authoritative tests.
- Confuse style preferences with assurance findings.

## Compact example

Requirement: payments of £10,000 or more require approval. Tests cover £9,999.99 and £10,000.01 but omit £10,000. The suite is green, yet mutation from `>=` to `>` survives. Verdict: **FAIL**. Blocking finding: the inclusive threshold is not protected. Recommended addition: strengthen the authoritative policy test with the exact-boundary case and show that the mutation fails.
